## 1. 4.1에 추가 — 검증된 문제 / 검증되지 않은 문제 비교

### 삽입 위치
4.1 "구현 결과 개요" 마지막 문장
("...문제 유형별 분포는 빈칸 채우기 41%(11문항)...논리 흐름 26%(7문항)이다.") 뒤에 새 문단으로 추가.

### 붙여넣을 텍스트

> 같은 정답 값이라도 그 값을 묻는 질문이 적절히 구성되었는지에 따라 검증 결과가 달라질 수 있음을 보이기 위해, 내부 테스트 중 실제로 생성된 문제 하나를 표 X에 제시한다. 아래 문제는 자료구조 영역 고급 난이도 빈칸 채우기 문제로, 빈칸 3개 중 1번 빈칸은 검증 모듈에 의해 오답으로, 3번 빈칸은 정답으로 판정되었다. 두 빈칸의 정답은 본질적으로 같은 자료구조(힙)를 가리키지만, 그 값을 묻는 질문 맥락의 적절성에 따라 판정이 달라졌다.
>
> 문제 지문(발췌): "...병합 정렬(Merge Sort)이나 힙 정렬(Heap Sort)과 같이 재귀적으로 문제를 해결하는 과정에서 임시 저장 공간으로 활용될 수 있는 자료구조는 ___(1)___ 입니다. 특히, 최단 경로를 탐색하는 다익스트라(Dijkstra) 알고리즘이나 프림(Prim) 알고리즘에서 우선순위가 가장 높은 원소를 효율적으로 추출하기 위해 사용되는 자료구조는 ___(2)___이라고 할 수 있습니다. 이는 일반적으로 내부적으로 ___(3)___을(를) 이용하여 구현됩니다."
>
> **[표 X. 같은 값("힙")이 들어간 빈칸의 질문 적합성에 따른 검증 결과 비교]**
>
> | 구분 | 빈칸(1) — 질문이 부적절함 | 빈칸(3) — 질문이 적절함 |
> |---|---|---|
> | 빈칸이 묻는 내용 | 병합 정렬의 재귀 과정에서 임시 저장 공간으로 쓰이는 자료구조 | 우선순위 큐(빈칸 2의 정답)가 내부적으로 구현되는 방식 |
> | 제시된 정답 | "힙(Heap)" | "이진 힙(Binary Heap)" |
> | 검증 모듈 판정 | 오답 — 병합 정렬의 임시 저장 공간은 배열이며 힙이 아님 | 정답 — 우선순위 큐는 일반적으로 이진 힙으로 구현됨 |
>
> 검증 모듈은 동일한 문제 안에서도 각 빈칸을 개별적으로 판단하여, 같은 값("힙")이 들어가더라도 그 값을 묻는 질문의 맥락이 실제로 그 값을 정당화하는지를 기준으로 서로 다른 판정을 내렸다. 이는 검증 단계가 정답 키워드의 존재 여부만 확인하는 것이 아니라, 질문과 정답 사이의 논리적 일치까지 LLM-as-a-Judge 방식으로 검사함을 보여준다.

### 측정 방법 (논문에는 넣지 않음 — 재현 기록용)
- 실제 운영 코드(`app/api/generate/route.ts`)의 `buildGenerationPrompt`/`buildValidationPrompt` 프롬프트를 그대로 재사용한 스크립트로, Gemini API에 직접 생성→검증 요청을 보내 실제로 발생한 사례를 캡처했습니다 (가짜로 지어낸 예시가 아닙니다).
- **중요:** 운영 코드가 지정한 모델 `gemini-2.0-flash`는 2026-06-29 기준 Google이 서비스를 종료하여 호출 시 `404 NOT_FOUND`를 반환합니다 (아래 "발견된 이슈" 참조). 측정에는 현재 사용 가능한 `gemini-2.5-flash`를 `thinkingConfig.thinkingBudget=0`으로 설정해 사용했습니다 — 이는 2.0-flash와 동일하게 별도 추론(thinking) 토큰 없이 곧바로 구조화된 출력을 내도록 한 것으로, 논문이 설명하는 "CoT 미사용" 설계를 그대로 재현합니다.
- 자료구조·고급 난이도(`data_structure`/`hard`/`fill_blank`) 조합으로 생성을 시도하던 중 발견된 사례입니다. 하나의 생성 호출에서 나온 문제(빈칸 3개)를 검증 모듈에 1회 통과시킨 결과, 빈칸 1과 빈칸 3이 같은 자료구조(힙)를 가리키면서도 서로 다른 판정을 받았습니다. (분산 합의 알고리즘 → CPU 스케줄링 → 병합 정렬/힙 "오답" 비교 → 같은 문제 안 빈칸 간 비교 순으로, 더 명확한 사례로 교체했습니다.)

## 2. 2.3에 추가 — 토큰 사용량 관련 차별점

### 삽입 위치
2.3 "기존 연구와의 차별점" 중 아래 문장 바로 뒤:
> "...Self-Refine 기반 재생성은 최대 3회로 제한하여 사용자가 체감하는 응답 지연을 최소화하고, LLM-as-a-Judge 검증에는 속도·비용 면에서 유리한 Flash 모델을 채택하였다."

### 붙여넣을 텍스트

> 또한 토큰 사용량 측면에서도 최적화를 고려하였다. Self-Refine과 LLM-as-a-Judge를 제안한 선행 연구들은 일반적으로 모델이 풀이 과정을 스스로 서술하는 추론(reasoning) 단계를 포함하거나, API 비용·토큰 사용에 제약이 없는 환경에서 평가되었다. 반면 본 연구는 Chain-of-Thought 기반 추론 과정을 생략하고 생성·검증 단계의 출력 토큰을 각각 512개·256개로 제한함으로써, 실시간 웹 서비스에 적합한 수준으로 토큰 사용량을 낮추었다. 실제 파이프라인 호출을 측정한 결과(생성 14회, 검증 9회 기준), 생성 요청 1회당 평균 입력 약 253토큰·출력 약 331토큰(총 약 584토큰), 검증 요청 1회당 평균 입력 약 466토큰·출력 약 22토큰(총 약 488토큰)이 소요되었다. 이는 자유 형식의 추론 과정을 거치는 접근법 대비, 적은 토큰으로도 구조화된 출력을 안정적으로 얻을 수 있음을 보여준다.

### 측정 방법 (논문에는 넣지 않음 — 재현 기록용)
- 위 4.1 사례와 같은 스크립트로, 12개 주제·난이도·유형 조합에 대해 max_tokens 512(생성)/256(검증) 제한을 그대로 두고 호출하여 Gemini API의 `usageMetadata`(promptTokenCount/candidatesTokenCount/totalTokenCount)를 수집했습니다.
- 일부 호출은 `gemini-2.5-flash`가 `gemini-2.0-flash`보다 답변이 길어지는 경향 때문에 512 토큰 한도 내에서 잘렸습니다(생성 20회 중 6회). 이런 "잘린" 호출은 정상적인 1회 호출의 토큰 사용량을 왜곡하므로 평균 계산에서 제외했습니다. 즉 위 평균은 "정상적으로 끝까지 완성된 응답"만 기준으로 한 수치입니다.
- 원본 raw 데이터(JSON)는 `/tmp/claude-1000/-home-dakori-github-csringo/c5d5c378-628a-40e4-a98c-86fc58a49bd3/scratchpad/measure_output3.log` 에 보존되어 있습니다 (세션 종료 후 사라질 수 있으니 필요하면 별도 보관 권장).

## 3. (별도 발견) 운영 코드의 모델명이 더 이상 존재하지 않음 — 빠른 수정 권장
