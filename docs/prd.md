## 1. 제품 개요 & 비전

### 1.1 제품 한 줄 정의

CS링고는 **비전공 주니어 개발자와 CS 전공 대학생**이 **매일 5~10분 마이크로 레슨과 게임화된 인출 연습**으로 **컴퓨터 과학 기초 개념을 장기 기억으로 굳히고 기술 면접 자신감을 얻도록** 돕는 웹 서비스다.

---

### 1.2 제품 비전

3~5년 후 CS링고는 한국 개발자 취업 준비생이라면 누구나 거치는 "CS 기초 습관화의 표준 플랫폼"으로 자리 잡는다. 단순한 문제 풀이 도구를 넘어, AI가 개인별 약점을 분석해 최적화된 학습 경로를 제시하는 적응형 CS 교육 서비스로 진화하며, 국내 부트캠프·대학교와 파트너십을 통해 연간 10만 명 이상의 개발자 커리어 성장에 기여한다. 궁극적으로 CS 기초가 취업의 장벽이 아닌 모든 개발자의 기본 자산이 되는 생태계를 만든다.

---

### 1.3 핵심 가치 제안 (Value Proposition)

**① 5분이면 충분한 CS 학습**  
지하철 한 정거장, 자기 전 침대에서, 점심 식사 후 5분. CS링고의 마이크로 레슨은 가장 바쁜 취준생도 "오늘 하나는 했다"는 성취감을 느낄 수 있도록 설계되었다. 긴 강의나 두꺼운 교재 없이도 꾸준히 쌓이는 CS 지식을 경험할 수 있다.

**② 읽기가 아닌 '직접 풀기'로 기억하는 방식**  
코드 빈칸 채우기, 블록 드래그 순서 배열, 로직 흐름 맞추기 — CS링고의 문제는 단순 객관식이 아닌 인출 연습(Active Recall) 기반이다. 뇌가 직접 개념을 꺼내는 과정에서 기억이 강화되며, 면접장에서 실제로 설명하는 능력까지 함께 향상된다.

**③ 게임처럼 지속되는 학습 동기**  
하트를 아끼며 신중하게 풀고, 스트릭이 끊길까 봐 오늘도 앱을 연다. XP가 쌓이고 리그가 올라가는 경험은 학습 자체를 보상으로 만든다. 듀오링고가 언어 학습을 습관으로 만든 것처럼, CS링고는 CS 학습을 루틴으로 만든다.

**④ 나의 약점을 아는 AI 복습 큐**  
틀린 문제는 잊혀지지 않는다. Claude API가 오답 패턴을 분석해 가장 취약한 개념을 복습 큐에 자동으로 추가한다. 매번 새 내용을 배우는 것이 아니라, 아직 내 것이 되지 않은 개념을 반복 노출해 진짜 이해로 이어지게 한다.

---

### 1.4 제품이 해결하는 핵심 문제

**층위 1: 내용 — CS 기초가 너무 방대하고 어렵게 느껴진다**  
현재 상황: 비전공 부트캠프 수료생은 6개월간 실전 웹 개발을 집중적으로 배우지만, 자료구조·OS·네트워크 같은 CS 기초는 체계적으로 배울 기회가 없다. CS 전공생조차 학기 중 배운 내용이 시험이 끝나면 휘발된다.  
문제: 기존 학습 자료는 대학 교재 수준의 분량과 깊이를 전제로 설계되어 있어, 바쁜 취준생이 "어디서부터 시작해야 하는지"조차 알기 어렵다.  
영향: 기술 면접 CS 질문 앞에서 머릿속이 하얘지고, 준비 부족으로 인한 불합격이 반복되며 자신감이 낮아진다.

**층위 2: 습관 — 한번 시작해도 이틀을 넘기지 못한다**  
현재 상황: "CS 공부해야지"라는 다짐과 함께 유튜브 강의나 인프런 강좌를 결제하지만, 평균 완강률은 10%에 불과하다.  
문제: 긴 강의 영상은 몰아서 보기엔 좋지만 매일 짧게 학습하는 루틴을 만들기 어렵고, 며칠 빠지면 죄책감에 아예 포기한다.  
영향: 학습이 이벤트(몰아보기)로 남고 습관(매일 조금씩)으로 자리잡지 못한다.

**층위 3: 동기 — 진도와 성장이 눈에 보이지 않아 중도에 그만둔다**  
현재 상황: 교재를 읽거나 강의를 봐도 "내가 얼마나 알고 있는지"를 즉각 확인할 방법이 없다.  
문제: 성취감을 주는 피드백 루프가 없어 동기가 빠르게 소진된다. 게임화가 없는 학습 도구는 의지력에만 의존한다.  
영향: CS 지식이 쌓이더라도 그것을 체감하지 못해 "나는 CS를 못 한다"는 부정적인 자기인식이 강화된다.

## 2. 문제 정의 & 시장 분석

### 2.1 문제 정의 (Problem Statement)

**상황 (Situation)**  
2024년 현재, 개발자의 76%가 GitHub Copilot·ChatGPT 같은 AI 코딩 도구를 일상적으로 사용한다(Stack Overflow Developer Survey 2024). 코드를 직접 타이핑하는 시간은 줄었지만, 채용 시장에서는 역설적으로 CS 기초 지식을 검증하는 기술 면접의 비중이 높아졌다. "AI가 코드를 짜도 설계하고 디버깅하는 사람은 인간"이라는 인식 때문이다.

**문제 (Complication)**  
기술 면접을 준비하는 비전공 주니어 개발자와 CS 전공 대학생 모두 "CS를 공부해야 한다"는 것을 알지만, 실천하지 못한다. LeetCode는 이미 어느 정도 알고 있어야 풀 수 있고, CS50은 영어로 된 긴 강의 영상이라 진입장벽이 높다. 인프런·Udemy 강좌는 강의 단위로 구성되어 있어 매일 5분씩 루틴을 만들기 어렵다. 결국 "CS 공부"는 벼락치기 형태로 이루어지다가 면접이 끝나면 금방 잊혀진다.

**결과 (Implication)**  
Ebbinghaus의 망각 곡선에 따르면, 한 번 학습한 내용의 50% 이상이 24시간 안에 잊힌다. 짧은 반복 학습 없이 몰아서 공부하는 방식은 장기 기억 형성에 비효율적이다. 그 결과, 취준생은 같은 개념을 여러 번 다시 공부해야 하고, 면접에서 알고 있지만 설명하지 못하는 경험을 반복한다. 이는 합격률 저하와 자신감 상실로 이어지며, 개발자 커리어의 초기 단계에서 불필요한 장벽을 만든다.

---

### 2.2 사용자 Pain Point 분석

**그룹 A: 비전공 부트캠프 수료 주니어 개발자**

1. "포트폴리오는 자신 있는데 CS 질문만 나오면 식은땀이 난다." — 6개월 동안 React와 Node.js만 파다 보니 자료구조나 OS 개념이 뭔지는 알아도 면접에서 말로 설명하기가 너무 어렵다. 말문이 막히는 순간 그동안의 준비가 다 무너지는 느낌이다.
2. "인프런 CS 강의를 세 번 결제했는데 한 번도 완강을 못 했다." — 매번 '이번엔 다르다'며 시작하지만, 하루 이틀 지나면 우선순위에서 밀리고 결국 0.3x 배속으로 틀어놓다가 리스트에서 지운다. 돈은 돈대로 쓰고 자책감만 남는다.
3. "내가 얼마나 알고 있는지 기준점이 없어서 불안하다." — 어느 날은 해시맵을 완벽하게 이해한 것 같은데, 다음 날 면접에서 비슷한 질문이 나오면 또 버벅인다. 내 CS 수준이 어느 정도인지 객관적으로 알 방법이 없다.

**그룹 B: CS 전공 대학생**

1. "기말고사 때 다 알았는데 방학 지나면 싹 잊힌다." — 운영체제 교수님 강의를 열심히 들어서 A+을 받았는데, 6개월 뒤 인턴 면접에서 프로세스와 스레드의 차이를 물어보면 머릿속에 아무것도 없다. 시험을 위해 외운 것과 진짜 이해한 것의 차이가 너무 크다.
2. "CS 기초는 알지만 코딩 테스트에 쓸 줄 모른다." — 학교에서 이론은 배웠지만 실제 코드로 어떻게 구현하는지, 어떤 문제에 어떤 자료구조를 쓰는지 연결이 안 된다. 이론과 실전 사이의 간극이 답답하다.
3. "CS 복습을 미루다 보면 인턴십 시즌에 벼락치기를 하게 된다." — 학기 중에는 과제와 팀 프로젝트로 바쁘고, 방학엔 쉬어야 할 것 같고. 결국 채용 시즌이 되면 CS 개념을 처음부터 다시 공부하는 상황이 반복된다. 이미 배웠던 걸 또 배우는 시간이 너무 아깝다.

### 2.3 시장 현황 & 기회

**글로벌 에듀테크 시장**  
글로벌 에듀테크 시장은 2023년 기준 약 2,040억 달러 규모로, 2028년까지 연평균 13.4% 성장해 약 3,800억 달러에 달할 것으로 추정된다(HolonIQ, 2024). 특히 모바일 마이크로러닝 세그먼트는 연평균 15% 이상 성장 중이며, Duolingo의 MAU가 2024년 1억 명을 돌파한 것이 마이크로러닝의 대중적 수요를 방증한다.

**국내 개발자 교육 시장**  
국내 IT 교육 시장은 2024년 약 1조 5천억 원 규모로 추정되며, 부트캠프·온라인 강의·코딩 테스트 준비 플랫폼이 주요 세그먼트를 이룬다. 연간 부트캠프 수료생은 약 3~5만 명으로, 이들 대부분이 CS 기초 보완의 필요성을 느끼는 잠재 사용자다. 대학 CS 전공생을 포함하면 연간 신규 타겟 사용자 풀은 10만 명 이상으로 추정된다.

**"매일 5분 CS 기초" 특화 서비스의 공백**  
현재 시장에는 CS 기초를 **습관화 중심**으로 접근하는 서비스가 존재하지 않는다. LeetCode는 알고리즘 코딩에, CS50은 강의 형식 CS 교육에, 인프런은 영상 강의에 집중한다. "매일 5~10분, 게임화, AI 맞춤, CS 기초 전 영역"을 동시에 충족하는 서비스의 공백이 명확하다.

### 2.4 기존 솔루션의 한계

**LeetCode**  
LeetCode는 알고리즘과 코딩 테스트 준비에서 독보적인 위치를 차지하지만, "CS를 처음 체계적으로 배우려는 사람"에게는 맞지 않는다. 문제 풀이를 위해 이미 어느 정도의 CS 지식이 전제되어야 하고, 게임화 요소가 제한적이며, 자료구조·알고리즘에 편중되어 OS·네트워크·DB 같은 이론 영역은 다루지 않는다. 진입 장벽이 높아 "스스로 CS를 잘 모른다"고 느끼는 초보자가 시작하기 어렵다.

**CS50**  
하버드의 CS50은 콘텐츠 품질로는 최고 수준이지만, 영어로 제공되는 긴 강의 영상 형식이라 한국 취준생이 매일 습관적으로 사용하기엔 부담이 크다. 강의를 수동적으로 시청하는 방식이라 인출 연습 효과가 낮고, 학습 진도가 느려지면 동기가 급격히 떨어진다.

**인프런**  
인프런은 다양한 CS 강좌를 제공하지만, 강의 단위(30분~수 시간)로 구성되어 있어 "오늘 10분만"이라는 마이크로러닝 습관과 맞지 않는다. 수강료를 결제한 후 완강하지 못하는 패턴이 반복되어 오히려 학습에 대한 죄책감을 만들기도 한다. 개인별 약점 분석이나 AI 기반 맞춤 복습 기능이 없어, 같은 내용을 반복해서 보더라도 취약점이 해소되지 않는다.

**CS 교재**  
"공룡책"(운영체제: 아브라함 실버샤츠)이나 "네트워크 하향식 접근" 같은 교재는 가장 깊이 있는 학습이 가능하지만, 분량과 난이도가 혼자 독학하기 어려운 수준이다. 챕터 단위로 읽어야 하는 구조라 이동 중이나 짧은 시간에 활용이 불가능하고, 읽기만 하는 방식이라 기억 유지율이 낮다.

### 2.5 왜 지금인가 (Why Now)

AI 코딩 도구의 급격한 확산은 아이러니하게도 CS 기초의 중요성을 더욱 부각시켰다. GitHub Copilot과 ChatGPT가 반복적인 코드 생성을 대체하면서, 채용 담당자들은 "AI가 못 하는 것" — 즉 시스템 설계, 복잡한 디버깅, 성능 최적화, 그리고 이를 뒷받침하는 CS 기초 이해력 — 을 더욱 엄격하게 검증하기 시작했다. 2024~2026년 개발자 채용 시장에서 기술 면접의 CS 질문 비중이 높아진 것은 이러한 흐름의 직접적인 결과다.

동시에, Duolingo가 하루 5분 언어 학습 습관을 전 세계 5억 명에게 만들어낸 것을 보며, 마이크로러닝의 효과에 대한 사용자 인식이 크게 높아졌다. "짧게 자주"라는 학습 방식이 대중적으로 검증된 지금이야말로, CS 교육에 동일한 접근법을 적용하기에 최적의 타이밍이다.

마지막으로, Claude API를 비롯한 AI 서비스의 접근성이 높아지면서 1인 개발로도 개인 맞춤형 학습 경험을 구현하는 것이 가능해졌다. 과거에는 수십 명의 엔지니어와 막대한 데이터가 필요했던 적응형 학습 시스템을, 지금은 Claude API와 Supabase를 조합해 소규모 팀도 만들 수 있다. CS링고는 이 세 가지 흐름 — AI 시대의 CS 기초 수요, 마이크로러닝의 대중화, AI 기술의 민주화 — 이 정확히 교차하는 지점에 있다.

## 4. 핵심 기능 명세 (Functional Requirements)

### 4.1 마이크로 레슨

**기능 개요**  
마이크로 레슨은 자료구조·알고리즘·OS·네트워크·DB·컴퓨터구조 6개 분야를 각각 5~10분 내에 완료할 수 있는 카드형 학습 단위로 세분화한 콘텐츠 시스템이다. 사용자는 한 번에 한 레슨씩 순차적으로 학습하며, 각 레슨은 개념 설명 카드와 인출 연습 문제로 구성된다.

**사용자 스토리**
1. 나는 취준 주니어 개발자로서, 지하철 출퇴근 시간에 자료구조 개념을 복습하기 위해, 5분 이내에 완료할 수 있는 짧은 레슨을 원한다.
2. 나는 CS 전공 대학생으로서, 수업에서 배운 내용이 잘 이해되지 않을 때, 쉬운 언어로 핵심을 다시 설명해 주는 카드를 원한다.
3. 나는 CS링고 사용자로서, 오늘 어떤 레슨을 해야 하는지 고민하지 않도록, 대시보드에서 다음 레슨을 바로 시작할 수 있기를 원한다.
4. 나는 학습 중 이탈한 사용자로서, 다음에 돌아왔을 때 중간부터 이어서 학습하기 위해, 레슨 진도가 자동 저장되기를 원한다.

**세부 요구사항**
1. 코스는 6개 분야(자료구조·알고리즘·OS·네트워크·DB·컴퓨터구조)로 구성된다.
2. 각 코스는 여러 챕터로 나뉘며, 챕터는 2~5개의 레슨으로 구성된다.
3. 레슨은 개념 카드(3~7장)와 문제(2~5개)로 구성되며, 전체 소요 시간은 5~10분이다.
4. 카드 유형: 텍스트+이미지 개념 카드, 코드 스니펫 카드, 비교 카드(A vs B), 요약 카드.
5. 완료 조건: 모든 카드를 확인하고 문제를 제출(정답/오답 무관)해야 레슨 완료 처리된다.
6. 레슨 진도는 Supabase에 실시간 저장되며, 페이지 이탈 후 재방문 시 마지막 카드부터 재개한다.
7. 첫 방문 사용자에게는 온보딩 레슨(5분)을 제공하여 서비스 사용법을 익힌다.
8. 레슨 완료 시 XP가 지급되고 완료 애니메이션이 표시된다.

**인수 조건**
- Given 사용자가 자료구조 챕터 1의 레슨을 시작했을 때, When 모든 카드를 스와이프하고 문제를 제출하면, Then 레슨 완료 처리되고 XP가 지급된다.
- Given 사용자가 레슨 도중 앱을 닫았을 때, When 다시 해당 레슨에 진입하면, Then 마지막으로 본 카드부터 이어서 학습할 수 있다.
- Given 레슨이 개념 카드 5장과 문제 3개로 구성될 때, When 측정하면, Then 전체 완료 시간이 10분 이내여야 한다.

### 4.2 인출 연습 문제

**기능 개요**  
인출 연습 문제는 단순 객관식을 지양하고, 사용자가 직접 코드를 완성하거나 순서를 배열하는 능동적 참여 방식의 문제 시스템이다. 코드 빈칸 채우기, 블록 드래그 순서 배열, 로직 흐름 맞추기 3가지 유형으로 구성되며, 오답 시 즉각적인 해설을 제공한다.

**사용자 스토리**
1. 나는 학습자로서, 개념을 읽기만 하는 것이 아니라 직접 써보면서 기억을 강화하기 위해, 코드 빈칸 채우기 문제를 원한다.
2. 나는 학습자로서, 알고리즘 실행 순서를 헷갈려 할 때, 직접 블록을 드래그해서 순서를 배열하는 문제를 원한다.
3. 나는 오답을 낸 학습자로서, 왜 틀렸는지 바로 이해하기 위해, 즉각적인 해설 카드를 원한다.
4. 나는 학습자로서, 문제를 다시 풀어보고 싶을 때, 복습 큐를 통해 동일 문제를 다시 만나고 싶다.

**문제 유형별 세부 요구사항**

*코드 빈칸 채우기:*
- 코드 스니펫의 핵심 부분을 `____` 형태로 빈칸 처리하여 표시한다.
- 사용자는 텍스트 입력 또는 선택지 클릭으로 빈칸을 채운다.
- 대소문자 구분 없이 정답 처리한다. (언어 특성에 따라 예외 처리 가능)
- 제출 버튼 또는 엔터로 제출한다.

*블록 드래그 순서 배열:*
- 코드 블록 또는 개념 블록이 섞인 순서로 제시된다.
- 사용자는 터치 드래그(모바일) 또는 마우스 드래그(데스크탑)로 순서를 재배열한다.
- 제출 후 정답 순서와 비교하여 맞은 블록/틀린 블록을 색상으로 표시한다.

*로직 흐름 맞추기:*
- 알고리즘 또는 시스템 동작의 단계가 빠진 채로 제시된다.
- 빠진 단계를 보기에서 선택해 흐름도에 삽입한다.
- 여러 빈칸이 있을 경우 순서대로 처리한다.

**오답 처리 흐름**
1. 오답 제출 시: 하트 1개 감소 (애니메이션), "아쉬워요!" 피드백 표시.
2. 즉각 해설 카드 표시: 정답과 이유를 2~4문장으로 설명.
3. 오답 데이터를 `wrong_answers` 테이블에 기록 (문제 ID, 오답 내용, 타임스탬프).
4. 해당 문제를 복습 큐에 추가 예약 (Claude API가 주기적으로 분석).
5. 하트가 0이 되면 학습 일시 중단, 하트 회복 안내 메시지 표시.

**인수 조건**
- Given 사용자가 코드 빈칸 채우기 문제에서 오답을 제출했을 때, When 처리되면, Then 하트 1개가 감소하고 해설 카드가 표시되어야 한다.
- Given 블록 드래그 문제에서 정답을 제출했을 때, When 처리되면, Then XP가 지급되고 정답 처리 피드백이 표시되어야 한다.
- Given 하트가 0개인 상태에서 오답을 제출했을 때, When 처리되면, Then 학습이 중단되고 하트 회복 안내가 표시되어야 한다.

### 4.3 게임화

**기능 개요**  
게임화 시스템은 사용자의 학습 지속성과 참여도를 높이기 위한 하트(생명), 스트릭(연속 학습일), XP(경험치), 리그 시스템으로 구성된다. 각 요소는 단기 동기(오늘 레슨 완료)와 장기 동기(리그 승급)를 동시에 자극하도록 설계되었다.

**하트 시스템 상세 규칙**
- 초기 하트 수: 5개
- 소모 조건: 인출 연습 문제 오답 1회 = 하트 1개 소모
- 회복 방법: ① 시간 경과 회복 (4시간마다 1개 자동 회복, 최대 5개), ② 광고 시청으로 즉시 1개 회복 (MVP에서는 미구현)
- 0개일 때 처리: 문제 풀이 불가, "하트를 회복하고 다시 도전하세요" 메시지 표시. 개념 카드 열람은 가능.

**스트릭 시스템 상세 규칙**
- 카운트 조건: 하루 1개 이상의 레슨을 완료하면 스트릭 +1 (UTC+9 기준 자정 리셋)
- 리셋 조건: 하루 레슨을 전혀 완료하지 못하면 스트릭 0으로 초기화
- 보호 아이템: MVP에서는 미구현 (Phase 3에서 "스트릭 보호 아이템" 추가 예정)
- 마일스톤: 7일, 30일, 100일 달성 시 특별 배지 지급

**XP & 레벨 시스템**
- XP 획득 조건: 레슨 완료 +15 XP, 문제 정답 +5 XP, 오답 후 재시도 정답 +2 XP
- 레벨 기준: 레벨 1(0 XP), 레벨 2(100 XP), 레벨 3(300 XP), 레벨 4(600 XP), 이후 레벨당 +400 XP 누적
- 레벨업 시 애니메이션과 "레벨 N 달성!" 알림 표시

**리그 시스템**
- 리그 단계: 브론즈 → 실버 → 골드 → 플래티넘 → 다이아
- 리그 기간: 주간 (월~일)
- 승급 조건: 주간 리그 내 상위 20% → 다음 리그로 승급
- 강등 조건: 하위 20% → 이전 리그로 강등
- MVP에서는 리그 표시 기능만 구현, 실제 경쟁 인원이 적을 경우 더미 데이터로 보완

**인수 조건**
- Given 사용자가 오답을 제출했을 때, When 처리되면, Then 하트가 즉시 1개 감소하고 현재 하트 수가 업데이트되어야 한다.
- Given 사용자가 오늘 첫 레슨을 완료했을 때, When 처리되면, Then 스트릭이 +1 증가하고 스트릭 알림이 표시되어야 한다.
- Given 사용자가 XP를 누적해 다음 레벨 임계값에 도달했을 때, When 레슨을 완료하면, Then 레벨업 애니메이션이 표시되어야 한다.

### 4.4 AI 맞춤 복습

**기능 개요**  
AI 맞춤 복습은 사용자의 오답 데이터를 Claude API로 분석해 가장 취약한 개념을 파악하고, 해당 개념을 다루는 문제를 복습 큐에 자동 추가하는 기능이다. 사용자가 별도의 설정 없이도 개인화된 복습 경험을 받을 수 있다.

**오답 데이터 수집 방식**
- 문제 오답 시 `wrong_answers` 테이블에 기록: `user_id`, `problem_id`, `user_answer`, `correct_answer`, `wrong_count`, `last_wrong_at`
- 동일 문제를 여러 번 틀릴 경우 `wrong_count` 증가

**Claude API 활용 방식**
- 호출 시점: 사용자가 레슨을 완료한 직후 (또는 일일 배치로 새벽 3시 실행)
- 전달 데이터:
  ```json
  {
    "user_id": "uuid",
    "wrong_answers": [
      { "problem_id": "...", "concept_tag": "hash_table_collision", "wrong_count": 3 }
    ],
    "recent_lessons_completed": ["data-structure-1", "data-structure-2"]
  }
  ```
- 프롬프트 구조: "다음 오답 패턴을 분석해 가장 취약한 개념 태그 3개와 복습 우선순위를 JSON으로 반환해줘."
- 응답 파싱: Claude가 반환한 JSON에서 `concept_tags` 배열을 추출해 해당 태그에 매핑된 문제 ID를 `review_queue`에 삽입

**복습 큐 동작 방식**
- 추가 조건: 동일 문제 2회 이상 오답 or Claude 분석 결과 우선순위 개념에 포함
- 노출 타이밍: 홈 대시보드의 "복습 필요" 섹션, 또는 레슨 완료 직후 "복습 추천" 팝업
- 우선순위 결정: `wrong_count` 높은 순 → `last_wrong_at` 최근 순

**사용자에게 보이는 UX 흐름**
1. 레슨 완료 → "오늘의 복습 문제가 생겼어요!" 알림 배너
2. 복습 화면 진입 → AI가 선별한 문제 리스트 (개념 태그 표시)
3. 복습 문제 풀기 → 정답 시 복습 큐에서 제거, 오답 시 큐 유지
4. 모든 복습 완료 시 "약점을 완전히 보완했어요!" 화면

**인수 조건**
- Given 사용자가 동일 문제를 2번 이상 틀렸을 때, When 레슨이 완료되면, Then 해당 문제가 복습 큐에 자동으로 추가되어야 한다.
- Given Claude API가 분석 결과를 반환했을 때, When 파싱하면, Then 우선순위 개념 태그 3개와 매핑된 문제 ID가 복습 큐에 삽입되어야 한다.
- Given 사용자가 복습 큐의 문제를 정답 처리했을 때, When 처리되면, Then 해당 문제가 복습 큐에서 제거되어야 한다.

---

### 4.5 인증 & 사용자 관리

**회원가입/로그인 방식**
- 지원 방식: Google OAuth 소셜 로그인 (MVP), 이메일+비밀번호 로그인 (Phase 2)
- Supabase Auth 사용, JWT 토큰 기반 세션 관리
- 로그인 상태는 Supabase 클라이언트가 자동 관리 (localStorage 기반)

**학습 데이터 저장 및 동기화**
- 모든 학습 데이터(진도, XP, 스트릭, 하트)는 Supabase PostgreSQL에 저장
- 클라이언트 측 낙관적 업데이트 후 서버 확인 방식으로 응답 속도 개선
- 다기기 접속 시 서버 데이터 기준으로 동기화

**인수 조건**
- Given 사용자가 Google 계정으로 로그인했을 때, When 처리되면, Then 30초 이내에 대시보드로 이동해야 한다.
- Given 로그인한 사용자가 레슨을 완료했을 때, When 데이터가 저장되면, Then 다른 기기에서 접속해도 동일한 진도가 반영되어야 한다.

## 5. 비기능 요구사항 (Non-Functional Requirements)

### 5.1 성능 (Performance)

**페이지 초기 로딩 시간**
- LCP(Largest Contentful Paint): 2.5초 이하 (Good 기준)
- FCP(First Contentful Paint): 1.8초 이하
- 측정 환경: Vercel Edge CDN, 한국 사용자 기준

**API 응답 시간**
- 레슨 불러오기(GET /api/lessons): 500ms 이하
- 문제 채점(POST /api/learning/submit): 300ms 이하
- AI 복습 큐 생성(POST /api/review/generate): 5초 이하 (Claude API 호출 포함, 비동기 처리)

**동시 접속자 처리**
- MVP 단계 목표: 동시 접속자 100명 처리 (Vercel Serverless 자동 스케일링 활용)
- Supabase 무료 티어: 초당 쿼리 200건 이내 설계

**모바일 네트워크(4G) 기준**
- 레슨 카드 이미지 lazy loading 적용, 첫 카드 표시까지 1초 이내
- 오프라인 상태에서 마지막 레슨 캐시 유지 (Service Worker, Phase 2)

---

### 5.2 보안 (Security)

**Supabase RLS 적용 범위**
- `user_progress`, `wrong_answers`, `review_queue`, `xp_logs`: 본인 데이터만 읽기/쓰기 가능
- `courses`, `chapters`, `lessons`, `problems`: 모든 로그인 사용자 읽기 가능, 쓰기 불가 (관리자만)
- RLS 정책 예시: `auth.uid() = user_id`

**인증 토큰 관리**
- Supabase JWT 토큰을 httpOnly 쿠키 또는 Supabase 기본 관리 방식 사용
- 토큰 유효 기간: 1시간, 리프레시 토큰: 7일

**Claude API 키 보호**
- `ANTHROPIC_API_KEY`는 서버 환경 변수에만 저장, 클라이언트에 절대 노출 금지
- API 호출은 Next.js Route Handler(서버 사이드)에서만 실행

**사용자 데이터 보호**
- 학습 기록, 오답 데이터는 본인만 접근 가능 (RLS)
- 개인식별 정보 최소 수집 (이메일, OAuth 제공 프로필 외 불필요 수집 금지)

### 5.3 접근성 (Accessibility)

- **WCAG 준수 수준:** WCAG 2.1 AA 목표 (MVP에서 핵심 흐름 우선 적용)
- **키보드 탐색:** 레슨 카드 넘기기, 문제 제출, 네비게이션 탭 이동 모두 키보드로 가능
- **스크린 리더:** 카드 텍스트, 버튼 레이블, 오답 피드백에 `aria-label` 적용
- **색각 이상:** 정답/오답 표시 시 색상만이 아닌 아이콘(✓/✗) 병용, 대비 비율 4.5:1 이상 유지

### 5.4 신뢰성 & 가용성 (Reliability & Availability)

- **목표 업타임:** 99.5% (Vercel + Supabase 무료 티어 현실적 기준)

### 5.5 유지보수성 & 확장성 (Maintainability & Scalability)

- **콘텐츠 확장성:** 레슨·문제 데이터는 DB에 저장되어 코드 변경 없이 추가 가능. JSON 기반 문제 포맷으로 관리자 입력 용이
- **기능 추가 영향 최소화:** Feature별 독립 Route Handler, 도메인별 독립 훅(useLearning, useGameification)으로 결합도 최소화

## 7. 데이터 모델 (Data Model)

### 7.1 엔티티 관계 설명

- **사용자(users)와 학습 진도(user_progress):** 1:N. 한 사용자는 여러 레슨 진도를 가질 수 있다.
- **사용자(users)와 오답 기록(wrong_answers):** 1:N. 한 사용자는 여러 오답 기록을 가질 수 있다.
- **사용자(users)와 복습 큐(review_queue):** 1:N. 한 사용자의 복습 큐에는 여러 문제가 포함될 수 있다.
- **코스(courses)와 챕터(chapters):** 1:N. 하나의 코스는 여러 챕터로 구성된다.
- **챕터(chapters)와 레슨(lessons):** 1:N. 하나의 챕터는 여러 레슨을 포함한다.
- **레슨(lessons)과 문제(problems):** 1:N. 하나의 레슨은 여러 문제를 포함할 수 있다.
- **문제(problems)와 오답 기록(wrong_answers):** 1:N. 하나의 문제는 여러 사용자의 오답 기록에 참조될 수 있다.
- **문제(problems)와 복습 큐(review_queue):** 1:N. 하나의 문제는 여러 사용자의 복습 큐에 포함될 수 있다.

### 7.5 데이터 흐름 요약

사용자가 문제를 풀고 오답을 내면:

1. 클라이언트가 `POST /api/learning/submit` 호출
2. 서버에서 정답 검증 → 오답 확인
3. `wrong_answers` 테이블 UPSERT: 기존 레코드면 `wrong_count +1`, `last_wrong_at` 업데이트; 없으면 새로 생성
4. `profiles` 테이블: `hearts -1` 업데이트
5. `xp_logs` 테이블: 오답이라도 "시도" XP는 미지급 (정답 시만 지급)
6. 응답 반환: 클라이언트에 오답 처리 결과 + 현재 하트 수 전달
7. (비동기) 레슨 완료 이벤트 발생 시: `POST /api/review/generate` 호출 → Claude API 분석 → `review_queue` 테이블에 취약 개념 관련 문제 INSERT

## 8. API 설계 (API Design)

### 8.1 API 설계 원칙

1. **RESTful 자원 중심:** URL은 명사(자원) 기반, HTTP 메서드로 행위 표현. `/api/learning/submit` (동사형)은 예외적으로 허용 (RPC 스타일 액션).
2. **통일된 JSON 응답 형식:** 성공/에러 모두 `{ success, data, error }` 구조를 준수.
3. **명시적 에러 처리:** HTTP 상태 코드를 의미에 맞게 사용하고, 에러 응답에 `code`와 `message` 필드 포함.
4. **Supabase JWT 인증:** 보호 엔드포인트는 `Authorization: Bearer <token>` 헤더 필수. 서버에서 `supabase.auth.getUser()` 검증.
5. **버저닝:** MVP에서는 `/api/` prefix 사용. 이후 `/api/v2/` 형태로 확장 (현재 버저닝 불필요).

---

### 8.2 공통 응답 형식

**성공 응답**
```json
{
  "success": true,
  "data": { ... }
}
```

**에러 응답**
```json
{
  "success": false,
  "error": {
    "code": "UNAUTHORIZED",
    "message": "로그인이 필요합니다."
  }
}
```

**공통 HTTP 상태 코드**
| 코드 | 사용 시점 |
|------|---------|
| 200 | 요청 성공 |
| 201 | 리소스 생성 성공 |
| 400 | 잘못된 요청 파라미터 |
| 401 | 인증되지 않은 요청 |
| 403 | 권한 없음 |
| 404 | 리소스 없음 |
| 500 | 서버 내부 오류 |

### 8.3 엔드포인트 목록

**인증 (Auth)**
| 메서드 | 경로 | 설명 | 인증 필요 | 요청 파라미터 | 응답 요약 |
|--------|------|------|---------|------------|---------|
| POST | /api/auth/signout | 로그아웃 | Y | - | success |

*주의: 로그인/회원가입은 Supabase Auth 클라이언트 SDK가 직접 처리 (별도 API 불필요)*

**콘텐츠 (Content)**
| 메서드 | 경로 | 설명 | 인증 필요 | 요청 파라미터 | 응답 요약 |
|--------|------|------|---------|------------|---------|
| GET | /api/courses | 전체 코스 목록 | Y | - | 코스 배열 |
| GET | /api/courses/[courseId]/chapters | 챕터 목록 | Y | courseId | 챕터 + 레슨 수 |
| GET | /api/lessons/[lessonId] | 레슨 상세 | Y | lessonId | 카드 + 문제 포함 |

**학습 (Learning)**
| 메서드 | 경로 | 설명 | 인증 필요 | 요청 파라미터 | 응답 요약 |
|--------|------|------|---------|------------|---------|
| POST | /api/learning/start | 레슨 시작 기록 | Y | lessonId | progress 객체 |
| POST | /api/learning/submit | 문제 정답 제출 | Y | problemId, answer | isCorrect, xpGained, hearts |

### 8.5 Claude API 연동 설계

**호출 시점**  
레슨 완료 직후 `POST /api/review/generate`가 호출될 때. 또는 매일 새벽 3시 배치로 전날 오답이 있는 사용자 전체에 대해 실행.

**Claude에 전달하는 프롬프트 구조**
```
당신은 CS 학습 분석 AI입니다. 다음은 사용자의 오답 데이터입니다.

오답 목록:
- 문제 태그: hash_table_collision, 오답 횟수: 3, 마지막 오답: 2026-05-07
- 문제 태그: stack_overflow, 오답 횟수: 2, 마지막 오답: 2026-05-06
- 문제 태그: process_scheduling, 오답 횟수: 1, 마지막 오답: 2026-05-05

이 데이터를 분석해서 가장 취약한 개념 태그 3개와 복습 우선순위(1~3)를 아래 JSON 형식으로만 응답해주세요:
{"weakConcepts": [{"tag": "...", "priority": N}, ...]}
```

**응답 파싱 방식**
```typescript
const response = await claude.messages.create({ ... });
const parsed = JSON.parse(response.content[0].text);
const weakConcepts = parsed.weakConcepts;
// weakConcepts의 tag 배열로 problems 테이블에서 문제 조회 후 review_queue INSERT
```

**응답 지연 대응**  
Claude API 응답은 비동기로 처리. `/api/review/generate`는 즉시 `{ queued: true }` 반환 후 백그라운드에서 처리. 완료 시 대시보드의 복습 알림이 다음 방문 시 표시됨. (실시간 푸시는 Phase 2)

### 9.3 핵심 아키텍처 결정 사항 (ADR)

**결정 1: 단일 레포 풀스택 구조 (Next.js 모노레포)**  
- 상황: 1인 개발로 빠른 MVP를 만들어야 하며, 프론트와 백엔드를 별도로 관리할 여유가 없다.
- 결정: Next.js App Router 내에 UI, API Route Handler, 비즈니스 로직을 모두 포함하는 단일 레포 구조.
- 이유: 코드 공유(타입, 유틸 함수)가 쉽고, 배포가 단순하며, 컨텍스트 전환 비용이 없다.
- 트레이드오프: 앱이 커지면 API Layer와 UI Layer 분리가 어려워질 수 있지만, MVP 규모에서는 유지보수성이 더 중요하다.

**결정 2: Supabase 선택 (자체 백엔드 서버 미구축)**  
- 상황: PostgreSQL, 인증, RLS, 실시간 기능이 모두 필요한데, 1인이 Express/NestJS 서버를 별도 운영할 시간과 비용이 없다.
- 결정: Supabase를 Backend-as-a-Service로 선택해 인증·DB·RLS를 위임.
- 이유: 무료 티어에서 MVP에 필요한 모든 기능을 제공하며, RLS로 보안 정책을 DB 레벨에서 선언적으로 관리 가능.
- 트레이드오프: Supabase 벤더 의존성이 생기지만, PostgreSQL 표준 SQL이라 마이그레이션 비용이 낮다.

**결정 3: Claude API를 서버 사이드에서만 호출**  
- 상황: API 키 노출, 비용 제어, 응답 파싱 로직 보호가 필요하다.
- 결정: 모든 Claude API 호출을 Next.js Route Handler(서버)에서만 수행. 클라이언트는 `/api/review/generate`를 통해 간접 호출.
- 이유: `ANTHROPIC_API_KEY`가 클라이언트 번들에 포함되지 않아 보안 유지. 비용 제어(사용자당 호출 횟수 제한)가 서버에서 가능.
- 트레이드오프: 약간의 지연(latency)이 생기지만, 보안 이점이 훨씬 크다.

### 9.4 보안 아키텍처

**클라이언트-서버 인증 흐름**
1. 사용자가 Google OAuth로 로그인 → Supabase Auth가 JWT 토큰 발급
2. 클라이언트는 Supabase 클라이언트 SDK가 자동으로 토큰 관리
3. Route Handler 호출 시 `Authorization: Bearer <token>` 헤더 자동 포함
4. 서버에서 `supabase.auth.getUser(token)`으로 검증

**RLS를 통한 데이터 접근 제어**  
모든 사용자 데이터 테이블에 RLS 활성화. 정책 조건 `auth.uid() = user_id`로 본인 데이터만 접근 보장. 콘텐츠 테이블(courses, lessons, problems)은 읽기 허용, 쓰기 차단.

**Claude API 키 보호**  
`ANTHROPIC_API_KEY`는 Vercel 환경 변수로만 등록. Next.js 규칙에 따라 `NEXT_PUBLIC_` 접두사 없이 설정하면 클라이언트 번들에 포함되지 않음.

**환경 변수 관리**  
`.env.local` (로컬 개발), Vercel 대시보드 환경 변수 (프로덕션). `.env.local`은 `.gitignore`에 포함, 저장소에 절대 커밋하지 않음.

### 10.4 논문 검증 지표

**연구 질문**  
"CS링고를 2주간 사용한 그룹은 미사용 그룹 대비 CS 기초 지식 테스트에서 더 높은 성취를 보이는가?"

**실험 설계**

1. **사전/사후 테스트**  
   - 가입 시 CS 기초 진단 테스트(20문항, 자료구조·OS·네트워크·DB·알고리즘 각 4문항) 자동 시행  
   - 2주 후 동일 또는 동등 난이도 테스트 재시행  
   - 점수 변화량(Pre-Post Gain Score) 측정

2. **사용량별 분석**  
   - 고사용 그룹(7일 이상 스트릭) vs 저사용 그룹(3일 미만)의 정답률 향상 비교  
   - 복습 큐 사용 여부에 따른 약점 개념 정답률 변화 분석

3. **사용자 인터뷰 (질적 연구)**  
   - 2주 후 5~10명 인터뷰: "CS링고 사용 전후 기술 면접 자신감 변화", "어떤 기능이 가장 도움이 됐는가"  
   - 반구조화 인터뷰, 주제 분석(Thematic Analysis) 적용

4. **수집 데이터**  
   - 정량: 레슨 완료 수, 정답률 추이, 스트릭 데이터, 진단 테스트 점수  
   - 정성: 인터뷰 녹취, 앱 내 자유 피드백 수집란
